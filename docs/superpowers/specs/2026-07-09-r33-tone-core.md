# R-33 tone core — `src/core/nutritionTone.ts` — Design Spec

**Parent spec:** `docs/superpowers/specs/2026-07-02-r33-ui-redesign-design.md` §5.
**Canvas authority:** `planificador-tone.jsx` (the logic) + `planificador-spec.jsx` (the living spec and its worked examples).

## 0. Summary

Port the canvas's semantic tone core into the app as a pure module, and **retire
`src/lib/macroStatus.ts`**, whose thresholds and state vocabulary diverge from the
canvas. Screens keep their current anatomy — the V4/V2 restyles belong to the §6
nutrition waves. This PR changes *which colour a bar or number takes*, not where
anything sits.

## 1. Why this is a replacement, not an addition

`macroStatus.ts` was written to fix an earlier "over anything = red" bug and
invented its own bands. It disagrees with the canvas in ways a user sees:

| case | shipped today | canvas |
|---|---|---|
| cut, target 2180, consumed 2050 | `budget` (blue) | `good` (green) |
| maintenance, 2480, consumed 2620 | `over` (red) | `slightOver` (amber) |
| bulk, 2780, consumed 2600 | `over` (red) | `low` (amber) |
| protein 20 % under target | `neutral` (silent) | `over` (red) |
| carbs +10 % in cut | `neutral` | `slightOver` (amber) |
| carbs, any, in bulk | `neutral` (grey) | `good` (green) |

Bands differ too: maintenance ±5 % (app) vs ±3 % (canvas); cut kcal by absolute
margins (+50/+100 kcal) vs percentages (+1.5 %/+5 %).

**Decision (owner, 2026-07-09):** the canvas wins. The `budget` state is dropped.
Protein under target now warns. See D-F17.

## 2. Module

`src/core/nutritionTone.ts` — pure, dependency-free, colocated `nutritionTone.test.ts`
(the `src/core/*.ts` + `*.test.ts` convention).

### 2.1 Vocabulary

```ts
type Tone = 'good' | 'onTarget' | 'slightOver' | 'low' | 'over' | 'neutral';
type Excess = 'neutral' | 'warn' | 'bad';
type PhaseType = 'cut' | 'maintenance' | 'bulk';
type Metric = 'kcal' | 'protein' | 'carbs' | 'fat' | 'fiber';
```

Canvas tone names are kept **verbatim** so the spec's worked examples transcribe
into golden vectors 1:1. They are colour-semantic, not direction-semantic:

- `good` / `onTarget` → green. `slightOver` / `low` → amber. `over` → red.
- **`over` means "outside the acceptable range, on the bad side" — not "above
  target".** Protein at −20 % is `over`. Fat below the essential floor is `over`.
  This is a wart inherited from the canvas palette keys; the module documents it.

`neutral` is ours: it covers a missing or non-positive target, which the canvas
never models. The canvas's `EXCESS.neutral` is unrelated (a bar-segment colour).

### 2.2 Classifiers

Ported verbatim from `planificador-tone.jsx`. `pct = (consumed - target) / target`.

`getKcalStatus(consumed, target, phase)`:
- cut: `pct > 0.05` → `over`; `pct > 0.015` → `slightOver`; else `good`.
- bulk: `pct < -0.05` → `low`; `pct < -0.015` → `slightOver`; else `good`.
- maintenance: `|pct| <= 0.03` → `onTarget`; else `pct > 0 ? slightOver : low`.

`getMacroStatus(metric, consumed, target, phase, fatFloorG?)`:
- protein: `pct >= -0.03` → `good`; `pct >= -0.10` → `slightOver`; else `over`.
- fiber: `consumed >= target * 0.9` → `good`; else `slightOver`. Overshoot never penalised.
- fat: `fatFloorG != null && consumed < fatFloorG` → `over`; `pct > 0.10` → `slightOver`; else `good`.
- carbs: `phase === 'cut' && pct > 0.08` → `slightOver`; else `good`.

`getExcessTone(status)`:
- `over` → `bad`; `slightOver` | `low` → `warn`; else `neutral`.

**Do not port `getExcessTone`'s `metric` and `phase` parameters** — the canvas
declares them and never reads them.

**Non-positive or missing target** → `neutral` tone, `neutral` excess, for every
metric. The canvas divides by `target` unguarded; we must not.

The canvas's fat rule reads `pct > 0.10 → slightOver` unconditionally, while the
spec prose says "más de +10 % sobre el objetivo **en déficit**". The code is the
authority per §1 of the parent spec: **no phase gate on fat.** Recorded here so the
divergence from the prose is deliberate, not an oversight.

### 2.3 Fat essential floor

The canvas never defines where `fatFloor` comes from; it is injected and only ever
the literal `48` in fixtures. Shipped code derives it as 20 % of target kcal ÷ 9.
Parent spec §5 says: a named constant in **g per kg of bodyweight**.

**Decision (owner):** follow the spec.

```ts
export const FAT_FLOOR_G_PER_KG = 0.6;
export function essentialFatFloorG(weightKg: number): number  // rounded; 0 if invalid
```

Derived at render, never stored (hard invariant 5). The three definitions coincide
near 48 g for a typical 80 kg / 2180 kcal athlete and diverge once weight and
energy stop correlating — which is the point: an essential floor is physiological.
See D-F18.

**Consequence:** bodyweight must reach the two consumers. `useLatestMeasurement()`
is the single upstream source. `useDailyTarget()` already reads `weight_kg`
internally and discards it — it will expose it, so the planning tree needs no second
query.

### 2.4 Classification result

```ts
interface ToneStatus {
  tone: Tone;
  excess: Excess;
  remaining: number;   // target - consumed
  overG: number;       // max(0, consumed - target)
  minFloorG?: number;  // fat only, when a floor was supplied
}
```

`fillPct` from the old `MacroStatus` is dropped — `MacroBar` computes its own
geometry and nothing else read it.

## 3. Rendering

`MacroBar` **already renormalises**: `denom = over ? consumed : target`, base and
excess segments sum to 100 %, target and floor ticks scale to `denom`. §5's
"bar renormalisation" requirement is therefore already satisfied. **Geometry does
not change; its test's pinned numbers must stay green.** Only the tone→class maps
are rewritten.

Tone → colour, everywhere (`MacroBar` fills, `DayTotalsCard`/`DaySummary` text):

| tone | class |
|---|---|
| `good`, `onTarget` | `bg-tone-good` / `text-tone-good` |
| `slightOver`, `low` | `bg-tone-warn` / `text-tone-warn` |
| `over` | `bg-destructive` / `text-destructive` |
| `neutral` | `bg-muted-foreground/50` / `text-muted-foreground` |

Excess → colour: `neutral` → `bg-excess-neutral`, `warn` → `bg-excess-warn`,
`bad` → `bg-excess-bad`.

`fatLow` is no longer a tone. The red frame and the help block key off
`metric === 'fat' && tone === 'over'`, which is unambiguous: canvas fat can never
reach `over` from being high (its worst high state is `slightOver`).

Captions (`totals.remainingG`, `totals.overG`, `totals.floorMet`, the fat-low block)
keep their current wording and i18n keys. §6 owns the "te faltan X g" rewrite.

## 4. Token reconciliation (closes D-F15)

D-F15 parked the invented dark values of `--tone-*` / `--excess-*` "pending
reconciliation with the canvas tone core". **There is nothing upstream to reconcile
with:** the canvas has no `--tone-*` and no `--excess-*` tokens at all — `TONE` and
`EXCESS` are hardcoded OKLCH literals in one `.jsx`, light-only. We own these slots.
D-F15 is marked resolved on that basis; its light values already match the canvas
literals exactly.

Token changes:
- **Delete `--tone-info`** (light + dark + `@theme` mapping). Its only reason to
  exist was the `budget` state, which is gone. Its three call sites all disappear
  with the tone-map rewrite.
- **Delete `--excess-good`** (light + dark + mapping). The canvas `EXCESS` has no
  `good`; a protein/fibre overshoot now paints `--excess-neutral`.
- **`--excess-neutral` becomes live.** It was defined and never used; it is now the
  excess segment for every non-warning state. (Also closes a parked follow-up.)
- Everything else stays.

Both colour gates must stay clean: no hex/oklch literals in `src/**/*.tsx`.

## 5. Golden vectors (Tier-1)

Transcribed from `planificador-spec.jsx`'s `<Case>` cards — the designer's own
asserted input → expected state. These are the test suite's backbone.

kcal, cut, target 2180: `2050 → good`, `2240 → slightOver`, `2320 → over`.
kcal, bulk, target 2780: `2600 → low`, `2730 → slightOver`, `2850 → good`.
kcal, maintenance, target 2480: `2470 → onTarget`, `2620 → slightOver`, `2350 → low`.
protein, target 168: `172 → good`, `156 → slightOver`, `138 → over`.
carbs, target 245: `238 cut → good`, `272 cut → slightOver`, `272 bulk → good`.
fat, target 68, floor 48: `60 → good`, `40 → over`, `80 → slightOver`.
fiber, target 30: `29 → good`, `22 → slightOver`, `38 → good`.

Plus the five-day `MiniWeek` fixture (cut, kcalTarget 2180, fatFloor 48) as one
multi-metric integration vector.

Beyond the canvas, pin the boundaries it leaves implicit: each threshold at exactly
`±1.5 %`, `±3 %`, `±5 %`, `−3 %`, `−10 %`, `+8 %`, `+10 %`, `90 %` (inclusive vs
exclusive per the operators above); `target <= 0` and `target` missing → `neutral`;
`consumed === 0`; `essentialFatFloorG` on 0, NaN, and a negative weight.

## 6. Out of scope

The V4 planner day header, `MacroChipV4`, the Diario V2 macro tiles and the Diario
weekly kcal chart (whose artboard TODO — "over=amber" is only right in cut — this
module now makes fixable). All belong to the §6 waves and land after this.

`nutri-modales-mobile.jsx` diverges from the shared palette (its own `MK_TONE` maps
`over` → gym blue, not red) and carries hardcoded per-row statuses. Flagged for the
Diario wave to resolve against the canvas owner; it does not affect this module.
