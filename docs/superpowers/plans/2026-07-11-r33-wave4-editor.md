# R-33 Wave 4 PR-B — Template editor Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rebuild the template editor on the components waves 3 and 4 already
shipped — and give it the mobile layout it has never had.

**Architecture:** The editor is the last screen still running on the pre-redesign
grid (`TemplateGrid` → `SlotCell` → `RecipePickerDialog`, plus `DaySummary`). It
is also the *only* grid in the app with no `md:` split: today a phone user pans a
desktop grid sideways. Almost everything it needs already exists — the trick is
to **generalise the planner's components rather than fork them**. A template is a
week without dates: `day_of_week` 0-6 instead of ISO dates. Mapping those onto a
reference Monday (which the editor page already does for its weekday labels)
lets `WeekStrip`, `TodayPlanList` and `PlannerMealCell` be reused untouched.

**Tech Stack:** React 18 + TS, Tailwind v4 `@theme` tokens, react-i18next
(`planning` namespace), react-hook-form + zod, TanStack Query, Vitest + Testing
Library.

## Global Constraints

- **Metric only** (kg/cm/g).
- **No schema / RLS / RPC change and no new PostgREST `.select()`.** PR-A did the
  one sanctioned schema change; this PR is pure UI on top of it.
- **`phase_type` is nullable and null is first-class** ("serves any phase"). The
  editor's new picker must be able to clear it back to `null`, and an untagged
  template must never inherit the user's *active* phase (a different concept:
  `useDailyTarget().phaseType`, which stays the source of the grid's macro
  targets — do not rewire targets to the template's own phase).
- **Every new string in ES *and* EN.** Zero hardcoded colours — only `@theme`
  tokens. Numbers carry `tnum`. Icon-only controls carry accessible names.
- `pnpm lint` + `pnpm build` + `pnpm test` green before any push.
- **No AI/Claude attribution anywhere** — plain conventional commits.
- **Do not open the PR until every gate has passed, the visual pass included.**
  A repo workflow auto-merges a `claude/*` PR the moment CI turns green.

## The reuse map (read this before touching anything)

| Need | Already exists | What it takes |
|---|---|---|
| Web day header (tone stripe, kcal hero, macro chips) | `DayHeaderCard` (wave 3) | It derives its weekday+number from an ISO date. Add an **additive** label variant so a template can pass "Lunes" with no date. |
| Web meal cell (bullets, copy, footer) | `PlannerMealCell` (wave 3) | **Nothing** — it is already date-agnostic (entries + callbacks). |
| Mobile day selector | `WeekStrip` (wave 3, selectable) | **Nothing** — feed it a reference Monday's 7 ISO dates and map the selection back to `day_of_week`. The editor page already builds exactly this reference Monday for its weekday labels. |
| Mobile day meal list | `TodayPlanList` (wave 3) | **Nothing** — its `TodayMeal` is `{mealIndex, mealTime, entries}`, no date. |
| Add/edit a recipe | `AddRecipeDrawer` (wave 3) | It builds its "destino" chip from a calendar date. Add an **additive** `destinationLabel` override. (This was flagged during wave 3 as the thing that would bite here.) |
| Phase picker | `PhasePicker` (wave 4 PR-A) | **Nothing.** |
| Copy a meal across days | `CopyMealDialog` (wave 3) | **Nothing** — the editor already uses it, with `allowAppend` correctly omitted (templates have no append path). |

**The payoff:** once the editor stops using them, `SlotCell`, `RecipePickerDialog`
and the editor's `DaySummary` usage have **no consumers left**. Task 5 deletes
them. That is the real end of the pre-redesign nutrition UI.

## Task 2: `templateWeek.ts` — the pure day/date bridge

**Files:** create `src/features/templates/templateWeek.ts` + test.

**Contracts:**
```ts
/** The 7 ISO dates of a reference Monday-based week, index = day_of_week (0=Mon). */
export function templateWeekDates(reference: Date): string[];
/** day_of_week for an ISO date within that reference week. */
export function dayOfWeekFor(dateIso: string, weekDates: string[]): number;
/** Per-day macro totals for the editor's headers, from the slot list + a recipe→per-serving map. */
export function templateDayTotals(
  slots: { day_of_week: number; recipe_id: string; servings: number }[],
  recipeMacros: Map<string, Macros>,
): Map<number, Macros>;   // keyed by day_of_week; days with no slots are absent
```

Tests must cover: a slot with an unknown `recipe_id` (macros not loaded yet)
contributes **zero**, not `NaN`; servings scale; several slots on one day sum;
`dayOfWeekFor` round-trips with `templateWeekDates`.

The reference Monday is `mondayOf(new Date())` — the editor page already computes
it for its weekday labels. These dates are **presentational only**: they never
reach the DB, and no slot ever stores one.

- [ ] Failing test → run → implement → green → commit (`feat(templates): pure day-of-week/date bridge for the editor`).

## Task 3: TemplateGrid (web) on the redesigned pieces

**Files:** rewrite `TemplateGrid.tsx`; rewrite its test.

Props stay as they are (`mealTimes`, `slots`, `onAdd`, `onUpdate`, `onRemove`,
`recipeMacros`, `targets`, `phaseType`, `weightKg`, `onCopyMeal`) **except** that
`onAdd`/`onUpdate` no longer carry a recipe — the cell now raises a request and
the page's drawer supplies the recipe (mirroring what wave 3 PR-B did to
`WeekGrid`):

```ts
onAddRequest: (dayOfWeek: number, mealIndex: number) => void;
onOpenEntry: (entry: PlannerCellEntry, dayOfWeek: number, mealIndex: number) => void;
onRemove: (rowId: string) => void;          // kept
onCopyMeal?: (dayOfWeek: number, mealIndex: number) => void;   // kept
```

Structure: the same `92px + 7` matrix as the planner's `WeekGrid` — a
`DayHeaderCard` per weekday (label variant: the full localized weekday; totals
from `templateDayTotals`, scored against `useDailyTarget()`'s targets, which the
page passes down), then one row per meal time with a `PlannerMealCell` per day.
No "today" outline (a template has no today) and no past-day dimming.

Tests: one header per weekday with its label; a cell's recipes listed; the meal
rows labelled by name + time; `onAddRequest`/`onOpenEntry`/`onCopyMeal` fire with
the right `(dayOfWeek, mealIndex)`.

- [ ] Failing test → run → implement → green → commit (`feat(templates): rebuild the web template grid on the redesigned day headers and cells`).

## Task 4: The editor page — responsive, with a phase picker

**Files:** rewrite `PlantillaEditorPage.tsx`; create `TemplateDayList.tsx`; create `PlantillaEditorPage.test.tsx`.

**Mobile (below `md`) — net-new, the whole point of this PR:**
`WeekStrip` (fed `templateWeekDates(refMonday)`, no kcal target line — pass the
day totals so it still tone-stripes each day) selects a `day_of_week`; below it,
`TemplateDayList` renders that day's meals via `TodayPlanList` (whose
`TodayMeal` shape already fits). Add and edit go through the page's single
`AddRecipeDrawer`, with `destinationLabel` = `"<Weekday> · <meal name> · <hh:mm>"`.

**Web (`md+`):** the rewritten `TemplateGrid`.

**The meta card** gains the `PhasePicker`, wired to a new `phase_type` piece of
form state, defaulting to the template's **stored** phase (`templateQuery.data
?.phase_type ?? null` — for a new template that is `null`, i.e. untagged; do NOT
default a new template to the user's active phase). Saving sends whatever the
picker holds. **This is what finally lets a template's phase be changed after
creation** — PR-A deliberately only preserved it.

Everything else the page does today survives: RHF + zod name/meal-times
validation, the copy-meal dialog (still `allowAppend`-less), the loading and
error states, and the save/cancel actions.

Tests must prove:
- the phase picker starts on the template's stored phase, and saving sends the picked one — including clearing it back to `null`;
- a NEW template starts untagged (`null`), NOT on the user's active phase;
- both trees render (CSS picks one), as on the planner — the page mounts the mobile stack and the web grid together, so use `getAllBy*` where the title appears twice;
- picking a day in the mobile strip switches the list to that day, and adding there writes to **that** `day_of_week` (make it discriminate: it must fail if the page always wrote to Monday);
- editing an existing slot updates it rather than adding a second one.

- [ ] Failing tests → run → implement → green → `pnpm lint && pnpm typecheck` → commit (`feat(templates): responsive template editor with its own phase picker`).
