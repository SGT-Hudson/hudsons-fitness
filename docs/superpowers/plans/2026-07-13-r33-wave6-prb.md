# R-33 wave 6 PR-B — plan

Spec: `docs/superpowers/specs/2026-07-12-r33-wave6-ingredientes.md` (read it —
it is the contract; this plan only sequences it, and records the decisions the
spec left open). Canvas (read-only, source of truth for layout):
`/mnt/d/dev/claude-design-hudson-fitness` — artboards `ingredientes-mobile-detail.jsx`
(method picker, scanner, create, edit) and `ingredientes-editor-web.jsx`.

PR-A shipped: the salt column end to end (**migration already applied to prod**),
the redesigned list, the full-screen search (D-F24), and the shared kit
(`IngredientSourceBadge`, `IngredientVerifiedCheck`, `IngredientRow`/`IngredientTable`/
`IngredientFilterBar`, `ingredientSource.ts`, `ingredientFilter.ts`,
`HighlightedText` + `findMatchRange`).

**PR-B is pure client work — no schema, no migration, no RPC.** It delivers:
the create/edit **routes**, the full-screen **scanner**, **auto-kcal**, and the
**editor with a live preview card** — while keeping the inline
create-then-select contract alive in a slim dialog.

## Decisions taken before this plan (do not re-litigate)

- **The slim dialog stays** (Gonzalo, 2026-07-13). The routes are the primary
  surface; a create-only dialog survives for exactly one job — `IngredientAutocomplete`
  and `AddIngredientSheet` create an ingredient mid-recipe and get it selected
  back. Rationale: `onSaved` stays a synchronous local callback; the alternative
  (routes + a return-to intent in router state) puts navigation state in the
  router for two callers and risks the one flow that already works.
- **The OFF payload must travel** (see Constraint 2 — the highest-risk part of
  this PR).
- **kcal auto-vs-manual is editing-session state, never stored.** No column.

## Global Constraints

Binding on every task. A violation is a failed review.

1. **`src/core/macros.ts` and `src/core/subMacros.ts` are FROZEN** (~30
   importers, dual-runtime Vite + Deno edge). Auto-kcal is a **new pure helper
   beside them** (`src/core/autoKcal.ts`) — dependency-free, no `@/` alias, no
   relative intra-core imports, so it stays Deno-safe like its neighbours. Note
   `src/lib/macros.ts` is a different thing (phase/target math) — not there.

2. **The OFF/scan payload is load-bearing.** Today `IngredientDialog` holds
   `pickedOFF: OFFSearchResult | null` and the submit branches on it:
   set ⇒ `importIngredientFromOFF` (writes `source='openfoodfacts'` +
   `external_id`), unset ⇒ `createManualIngredient` (`source='manual'`,
   `external_id` null). Splitting create across routes **must carry that product
   with the form**, or a scanned/imported product silently saves as a manual row
   with no EAN — an invisible data-integrity regression. Carry it in
   `location.state` on the route and as a prop on the slim dialog; the editor
   takes it as one explicit `offProduct?: OFFSearchResult | null` input and
   branches at submit exactly as today. Pin it with a test.

3. **`null` sub-macro = UNKNOWN, never 0** (sugar, satFat, salt). `ingredientToForm`
   maps `null` → blank (not `"0"`); `parseForm` maps blank → `null`. Already
   pinned by 16 tests in `IngredientFormFields.test.ts` — keep them green.

4. **An imported OFF kcal is NEVER auto-overwritten** (spec §3). OFF disagrees
   with Atwater by ±20% (rounding, fibre, polyols) and the label is the truth.
   So the editor's kcal mode initialises to **`manual`** whenever the form was
   seeded from OFF or a scan, and on `/:id/edit` of a stored row (a stored kcal
   is just a number — claiming it is "auto" would be a lie). It initialises to
   **`auto`** only on a blank manual create.

5. **The auto→manual switch must be reversible.** The canvas offers no way back;
   the spec requires an explicit "volver a automático" affordance, because
   otherwise it is a one-way trap. Track the override in **explicit state, not
   `formState.dirtyFields`** — the form uses `reset()` as a setter, which
   clobbers dirty tracking.

6. **The scanner engine is NOT rewritten.** Native `BarcodeDetector` + lazy
   `@zxing/browser` fallback + `isValidEan` re-validation on every decode + the
   track teardown all stay. This is a **mounting and chrome change**. The camera
   affordance stays gated on `(pointer: coarse)`; the typed-EAN path stays always
   available (that is what the web method picker uses).

7. **Do not break the three redesigned consumers.** `IngredientAutocomplete` +
   `AddIngredientSheet` (recipe editor, wave 5) and `AddToDaySheet` (Diario,
   wave 2) call `useLocalIngredientSearch(query, 12, enabled)` and read `id`,
   `ingredientDisplayName(ing, lang)`, `brand`, `kcal_per_unit`, `unit_type`.
   The Diario reaches into the **`ingredientes`** i18n namespace for
   `list.perUnit` / `list.per100g` — do not rename those keys. The
   `['ingredients', …]` query keys must not be renamed.

8. **Editing is ownership-gated.** Only `created_by_user_id === user.id` may
   edit (the list already computes this at `IngredientesPage.tsx:281`). Add a
   `canEditIngredient` helper mirroring `canEditRecipe` (`features/recipes/ownership.ts`)
   and guard the edit route — a deep link to a foreign row must redirect, not
   render an editor that fails on save. (Wave 5 shipped that hole; don't repeat it.)

9. **Every new page must be `vi.mock`ed in `src/app/router.test.tsx`.** That
   suite mocks every page module and does *not* mock `@/lib/supabase`; an
   unmocked new page drags the client in and dies in CI with no env vars — green
   local, red CI. This exact trap cost PR-A a CI round trip.

10. Every new user-facing string in ES **and** EN. Mobile-first (mobile artboard
    = base, web = `md:`+). Light **and** dark. Reuse the shared kit (`PageShell`,
    `ResponsiveDialog`, `EmptyState`, the shadcn primitives) — do not fork.

## Tasks

### Task 1 — Foundation: the pure helpers and the missing data hooks

No UI. Everything downstream depends on this, so it lands first and alone.

- **`src/core/autoKcal.ts` + `src/core/autoKcal.test.ts`** — Atwater `4P + 4C + 9F`
  over the parsed macro numbers, with the project's rounding convention. Pure,
  dependency-free, Deno-safe (see Constraint 1). Tier-1 tests: the arithmetic,
  rounding, blank/partial inputs (a blank macro contributes 0 to the derivation —
  that is a *derivation* input, not a stored sub-macro, so Constraint 3 does not
  apply here), and the override rule as a pure predicate if one is extracted.
- **`getIngredient(id)` + `useIngredient(id | null)`** — `src/features/ingredients/api.ts`
  + `hooks.ts`. There is **no single-ingredient fetch today**; `/:id/edit` needs
  one that survives a hard reload / deep link (reading the pool cache alone
  renders blank). Key `['ingredients', 'detail', id]`; null-arg disables the
  fetch (the `useRecipe` pattern).
- **`canEditIngredient(ing, userId)`** — mirror `features/recipes/ownership.ts`.
- **`offResultToForm(result)`** — extract the OFF→form mapping that is currently
  **written twice** inside `IngredientDialog` (the off-tab pick and the barcode
  `onResolved`). One function, used by the route, the scanner and the dialog.
  Preserves `null` salt/sugar/satFat (Constraint 3).
- **`firstIngredientError`** — wrap `pickFirstError` (`src/lib/zod.ts`) as the
  other features do (`firstRecipeError`, `firstTemplateError`). Today the dialog
  collapses every field error into one `errors.invalid` line; the editor page
  gets real per-field ordering.

Verify: `pnpm typecheck && pnpm test src/core src/features/ingredients`.

### Task 2 — The editor component (auto-kcal + salt + live preview card)

The shared body used by **both** the editor routes and the slim dialog. Spec §6
"The editor"; canvas `ingredientes-editor-web.jsx` + `ingredientes-mobile-detail.jsx`.

- Identidad (name, brand), the `unit_type` segmented control (g / ud), the macro
  block with **auto-kcal** (the `auto` chip; editing kcal directly takes it
  manual and drops the chip; an explicit "volver a automático" brings it back —
  Constraints 4 + 5), the sub-macros (azúcares, saturadas, fibra, **sal**), the
  origin card on edit (source badge + the EAN from `external_id` for OFF rows),
  and the **live preview card** (list-row replica, big kcal, macro triad,
  "reparto calórico" bar — recomputed from `watch()`, the `RecipeEditorForm`
  live-macros precedent).
- Takes `offProduct` (Constraint 2) and branches the submit: import vs create vs
  update. Keeps the OFF caveat line ("los valores vienen de la comunidad;
  compáralos con tu envase") — it is honest and the data warrants it.
- Reuses `IngredientFormFields` where it still fits rather than re-typing fields;
  `ingredientToForm` / `parseForm` / the zod schema stay the boundary.

Tier-2 tests: auto-kcal derives while you type; editing kcal overrides it and
the chip goes; "volver a automático" restores it; an OFF-seeded form starts
manual and its kcal is never overwritten; salt round-trips blank↔null; the
preview card tracks the form.

### Task 3 — The editor routes (`/new/manual`, `/:id/edit`)

Page shell around Task 2, on the `RecetaEditorPage` model (memoized `initial` —
its 6-line comment explains why: unrelated state churn must not give `initial` a
new identity or the reset-effect wipes the user's typing; `PageShell title
subtitle actions back`; guards above the early returns to keep hook order stable).

- `/recipes/ingredients/new/manual` — empty editor; accepts an OFF product or a
  scanned EAN via `location.state` (Constraint 2) and seeds from it.
- `/recipes/ingredients/:id/edit` — loads via `useIngredient`, **ownership-gated**
  (Constraint 8): a foreign row redirects to the list, it does not render.
- Rewire `IngredientesPage`: `onEdit` navigates to the edit route; drop `editing`
  state, `routeIntent` and the `defaultTab` prop. **The `?q=` round-trip must
  survive** — it is pinned by `IngredientesPage.test.tsx` ("round-trips an active
  `?q=` through the create dialog, in and out"); that test now describes routes,
  not a dialog, so rewrite it to assert the same *behaviour* through the new
  surface. Do not delete the assertion.
- Register the routes + `vi.mock` the new pages in `router.test.tsx` (Constraint 9).

### Task 4 — The method picker (`/new`)

Spec §6 "Method picker"; three cards (manual / buscar en OFF / escanear).
**Mobile promotes scan first; web puts the typed-EAN entry inline and states
plainly that camera scanning is mobile-only** — which matches the code, the
camera affordance is already `(pointer: coarse)`-gated. The OFF search panel
(today `OFFSearchPanel`, local to the dialog) becomes reachable from here; a pick
routes to `/new/manual` carrying the product (Constraint 2).

### Task 5 — The full-screen scanner (`/scan`)

Spec §6 "The scanner, full-screen". Mounting + chrome only (Constraint 6).

- Follow **`IngredientSearchPage`'s route shape** — a normal route inside
  `AppLayout` rendering a Radix takeover (`Dialog open` + portal + `fixed inset-0
  z-30`, `sr-only` DialogTitle, `onOpenChange` → navigate back). Its docblock
  explains why (focus trap, Escape, above the nav's `z-20`).
- Chrome: dark, the corner-bracket framing box (the canvas gets the scrim with a
  `0 0 0 9999px` shadow, not an overlay element), the scanning laser, a glass
  close/torch, and the "escribir código a mano" escape hatch.
- **States are ours to design** — the canvas drew only *scanning*. Build
  scanning / found / **not-found** / **permission-denied** from the canvas's
  vocabulary (the status pill is the state slot). Today permission denial falls
  into one generic `cameraError`; split it — a denied camera is a *fixable* user
  state and deserves its own copy.
- **Not-found routes to `/new/manual` pre-filled with the scanned EAN** (spec).
- Tests: mock the detector, assert the **states** — do not attempt a real camera
  in jsdom. The existing `BarcodeScanner.test.tsx` actually tests `BarcodeTab`
  (with the scanner stubbed) and exports it only for that; keep its five
  assertions alive against whatever replaces it.

### Task 6 — The slim dialog + closing wave 5's `AddIngredientSheet` gap

- Reduce `IngredientDialog` to **create-only**: `open`, `onOpenChange`,
  `defaultName`, `onSaved`. Drop `mode`, `initial`, `defaultTab`, and the
  tabs-as-navigation. `IngredientAutocomplete`'s contract (`defaultName={query}`,
  `onSaved={(ing) => onSelect(ing)}`) must survive **verbatim**.
- Wire **create-from-`AddIngredientSheet`** — the footer escape hatch its own
  docblock says wave 6 owns ("there is no create-ingredient route to send a thumb
  to"). `onSaved` → its `select(ing)` (so the quantity stepper appears), **not**
  `onAdd`. ⚠️ `AddIngredientSheet` is a **vaul Drawer on mobile** and the slim
  dialog would nest inside it — this is exactly the class of bug jsdom cannot
  see. **Drive it in a real browser** (both breakpoints) before calling it done;
  if nesting misbehaves, route out to `/new/manual` and return instead.
- `RecetaEditorPage.test.tsx` / `RecipeEditorForm.test.tsx` transitively render
  `IngredientDialog` — changing its import graph can break them.
