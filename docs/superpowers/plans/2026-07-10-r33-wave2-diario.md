# R-33 Wave 2 — Diario Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Restyle the food-diary ("Diario") screen to the R-33 design — a phase-status kcal ring, tone-aware macro tiles with progressive disclosure, restyled meal cards with "Plan" badges, a restyled per-meal quick-add strip, a phase-aware weekly kcal chart, and (md+) a right rail (kcal hero · 2×2 tiles · week chart · Cuerpo quick-measure card). The add/logging flow and full-screen quick search ship in a **second PR** (PR-B, outlined at the end).

**Scope split (this wave = 2 PRs):** The Diario wave has ~9 distinct surfaces; too large for one reviewable PR. Clean seam = *viewing the day* (PR-A, this plan) vs *logging into the day* (PR-B). Each is independently CI-greenable and shippable.

**Architecture:** All work stays inside `src/features/diario/` + `src/components/ui/`. The data layer is untouched (no schema/RLS/RPC/`.select()` changes in PR-A) — every number the redesign needs is already client-side:
- **consumed** macros/kcal = `sumMacros(logs.map(computeMealLogMacros))` (already in `DiarioPage`).
- **phase target** = `computePhaseTargets(activePhase, weight, bodyFat, tdee)` (already in `DiarioPage`).
- **"plan de hoy" footnote** = sum of `from_plan` meal_logs (free — flag already on each entry).
- **weekly kcal** = 6 past days from `daily_nutrition_history` (reuse the Progreso hook) + today's live consumed total. This is the *only* new read in PR-A; it reuses an existing `.select('*')` so no R-32 escape-hatch risk, but verify against a real DB per the standing rule.

**Tech Stack:** React 18 + TS, Tailwind v4 (PR-2 tokens in `src/index.css`), shadcn/ui, `src/core/nutritionTone.ts` (tone core), Vitest + RTL (jsdom).

**Spec:** `docs/superpowers/specs/2026-07-02-r33-ui-redesign-design.md` §6.2 + §5 + §7. Canvas references (read-only, `/mnt/d/dev/claude-design-hudson-fitness`): `src/mobile.jsx` (`DiarioRing`, `DiarioMacroBar`, `MobileMeal`, `MacrosDisclosure`, `MacroTile`), `src/diario-web.jsx` (`DiarioWebV2`: `KcalHero`, `MacroTile`, `MealSection`, week chart, Cuerpo card), `src/planificador-tone.jsx` (`TONE`/`EXCESS`, mirrored by the shipped tone core).

## Global Constraints

- **No AI/Claude attribution anywhere** — plain conventional commits, no `Co-Authored-By`, no "Generated with…".
- All new user-facing strings in **ES and EN** (`src/i18n/{es,en}/diario.json`).

Arbitrary geometry values (`rounded-[14px]`, `text-[9.5px]`, `size-[118px]`) are fine and expected — only *color* literals are banned.
- Tone → color mapping stays in the consumer (as today: `TEXT_TONE` in `DayTotalsCard`, `BASE_TONE`/`EXCESS_TONE` in `MacroBar`); extend those maps, do not invent a parallel system. Colors come from tone tokens (`tone-good`, `tone-warn`, `destructive`, `excess-*`, `--macro-*`).
- Section accent (`.section-nutri`) already lives on `<html>`; do not touch it. Dark mode (`.dark`) untouched — visual dark-mode fixes are opportunistic only.
- No schema/RLS/RPC changes. PR-A's one new read reuses the existing Progreso `daily_nutrition_history` select — no new `.select()` string.
- Every task ends green: `pnpm lint` + targeted test file; full relevant suite + clean `git status` before commit.
- `PageShell` mounts the mobile header **and** `PageHeaderV2` at once by design (CSS hides one). Page tests use `getAllByRole` — the title renders twice in jsdom. Do not "fix" it.

## Design decisions locked by this plan (record D-ids in the final task)

- **D-F19 — Single-arc kcal ring, not the canvas double-arc.** This app materializes plan meals into `meal_logs` (`from_plan=true`) that already count as consumed, so a "planificado (faint) vs registrado (solid)" split has no clean data source for *today* — the faint arc would sit hidden behind the solid one except when the user deletes plan meals. Per spec §6.2's authorized fallback, the ring is **single-arc: consumed / phase-target**, colored by `getKcalStatus(consumed, target, phase)`, with a "plan de hoy: {X} kcal" footnote derived free from the sum of `from_plan` logs. The double-arc is not deferred to later — it is incompatible with the pre-materialization model; if a true planned/eaten split is ever wanted it needs an "eaten" flag (net-new, out of scope, note for roadmap).
- **D-F20 — Macro display follows spec §6.2 text (tiles + progressive disclosure), not the canvas canonical render.** Canvas `DiarioMobile` shows 4 inline bars beside the ring; `MacrosDisclosure` (collapsible 2×2 tiles) is defined but unwired. Spec §6.2 explicitly says "macro tiles … + progressive disclosure," so **mobile = collapsible 2×2 `MacroTile` grid** (closed by default, toggle reveals), **web right rail = always-visible 2×2 tiles**. Both reuse one `MacroTile`.
- **D-F21 — Weekly chart data = `daily_nutrition_history` (past) + live today.** Phase-aware coloring via `getKcalStatus`/`getExcessTone` (the canvas hardcodes the cut rule; that is a documented TODO, not the target). Reuse the Progreso history hook; no new query string.
- **Strip-list (per spec §6.2):** notifications bell, "quema +340" burn readout. Both already opted out / absent in shipped chrome — just don't reintroduce.

**Build:**

Track circle = `--bg-sunken`; fill arc `strokeDasharray={circ}`, `strokeDashoffset={circ*(1-min(1,consumed/target))}`, `strokeLinecap="round"`. Props typed; no color literals (use `stroke-[color:var(--tone-…)]`? — no: keep tone→class in the consumer and pass a `className`/tone prop, mapping to `text-tone-good` etc. Resolve the SVG-stroke-from-token detail with a small `TONE_STROKE` class map, mirroring `TEXT_TONE`).
