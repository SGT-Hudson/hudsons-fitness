# R-33 wave 5 PR-B — the Recetas editor

Spec: `docs/superpowers/specs/2026-07-12-r33-wave5-recetas.md` (§7 "Editor" is the
contract; §5 and §6 bind too). PR-A shipped the list, the read view, the route
split and the prep-time field. This PR redesigns the **editor** — the last
pre-redesign nutrition surface — and closes two gaps PR-A opened.

Canvas (read-only, source of truth for layout): `/mnt/d/dev/claude-design-hudson-fitness`
— web: `RecetaEditorWebV2` + `RecetaCrearWebV2` (`src/receta-editor-web.jsx`);
mobile: `RecetaEditarMobile` + `RecetaCrearMobile` (`src/recetas-mobile-detail.jsx`)
and the `RecetaAddIngredienteMobile` sheet (`src/recetas-add-mobile.jsx`).

## Global Constraints

Binding on every task. A violation is a failed review.

1. **Metric-only.** Prep time is integer **minutes**; quantities in g/ud as today.
2. **DB is canonical; RLS is the sole boundary.** **This PR adds no migration and
   no RPC change** — `save_recipe` already takes everything the editor needs.
3. **Every new user-facing string in ES *and* EN**; no hardcoded copy; remove the
   i18n keys of any UI you retire.
4. **`src/features/recipes/macros.ts` is frozen** (~30 importers). So are the
   `['recipes', …]` react-query keys.
5. **The prep-time round trip is load-bearing.** `save_recipe` writes
   `p_prep_time_minutes` **unconditionally**, so a save that omits the value
   **wipes the column**. Today the value survives only because
   `recipeToEditorState` carries it through react-hook-form's `defaultValues`
   (pinned by tests in `RecipeEditorForm.test.ts` / `.tsx` — proven live). When
   you render the real input, that round trip must still hold and those tests
   must stay green.
6. **Reuse the shared kit before building anything new**: `ResponsiveDialog`
   (vaul Drawer <md / Radix Dialog ≥md), `RecipeMediaPlaceholder`,
   `RecipeMacrosCard` (PR-A's read-view macros card — extend it rather than
   forking; the editor's variant is titled "Macros en vivo" and needs the empty
   state), `IngredientAutocomplete`, `EmptyState`, the shadcn primitives in
   `src/components/ui/`.
7. Mobile-first: mobile artboard = base layout, web artboard = `md:`+.
8. **No new dependencies.** No AI/Claude attribution anywhere (plain conventional
   commits, no `Co-Authored-By`, no AI phrasing in comments).
9. jsdom traps: `PageShell` renders the title twice (`getAllBy*`); a `.test.tsx`
   rendering a supabase-importing component **fails in CI** unless the data hook
   is mocked; `asChild` + a function `className` silently corrupts the class;
   vaul grabs the pointer on pointerdown (the Pointer Capture polyfill in
   `src/test/setup.ts` handles it — do not remove it).

## Out of scope (deliberate)

- **Drag-to-reorder ingredients.** The canvas draws drag handles and
  `recipe_ingredients.display_order` exists, but a reorder UI needs a DnD
  library and constraint 8 forbids new deps. Keep `display_order` = row index,
  as today. Roadmap follow-up.
- **Structured steps, per-step photos, the steps card.** `instructions` stays one
  textarea (R-36). The read view renders it as step "1" — that is the whole
  story until R-36.
- **Photo upload** — the media slot stays `RecipeMediaPlaceholder`.
- **Private notes** (`user_recipe_refs.note` — would need an RPC change).
- **The barcode button** on the mobile add-ingredient sheet → wave 6
  (Ingredientes owns the scanner).

## Task 1 — The editor's frame: meta card, prep time, instructions, actions

**Goal:** `/recipes/new` and `/recipes/:id/edit` match the canvas everywhere
except the ingredients table (Task 2).

Current editor: `src/pages/RecetaEditorPage.tsx` + `RecipeEditorForm.tsx`
(RHF + zodResolver, `useFieldArray` for rows, a sticky `LiveMacrosPanel` aside).
Read both, then the four canvas artboards.

**Meta card** (`RecetaMetaEdit` / `RecetaMetaCreate` web, the mobile equivalents):
media placeholder tile (reuse `RecipeMediaPlaceholder`; on **create** there is no
recipe id yet — pick a stable hue source and say what you chose), a **borderless
title input**, and the meta fields: **Raciones**, **Tiempo**, **Etiqueta**
(meal-type chips — the existing multi-select, restyled).

**Prep time is the new input.** Integer minutes, optional; empty means "no time
recorded" and must send `null`. Two things to get right:
- Constraint 5 — the value must still round-trip on a save that does not touch it.
- `parsePrepTimeMinutes` (`src/features/recipes/schema.ts`) currently has **no
  upper bound**: `'99999999999'` passes validation, overflows `int4` at the DB and
  surfaces a raw Postgres error in the editor's error box. Now that a user can
  actually type it, add a sane maximum and its message (ES + EN), and test it.

**Instructions**: the existing single textarea, restyled per the canvas. Do not
build fake step rows.

**Actions**: Guardar (primary), Cancelar, and Eliminar (danger). The canvas's
mobile delete is a centred confirm modal with a preview; its inline-row delete
convention — **Cancelar always on the outside, so a sloppy thumb never lands on
Eliminar** — applies to Task 2's ingredient rows, not here.

**Live macros** — the right rail on web, stacked on mobile. PR-A already built
`RecipeMacrosCard` (totals vs per-serving, per-serving highlighted, kcal-share
distribution bar) for the read view. **Extend it**: the editor needs the "Macros
en vivo" title and the **empty variant** (both columns `—`, the bar replaced by
the "los macros se calcularán…" hint). Do not fork it, and do not regress the
read view. `LiveMacrosPanel` is the pre-redesign panel — retire it once nothing
uses it, and remove its dead i18n keys.

**Tier-2:** the editor renders an existing recipe's values (including prep time);
saving sends the prep time it loaded when the user never touched the field
(constraint 5); an out-of-range prep time is rejected at the form boundary with
the localized message.

## Task 2 — Ingredients: the table, the per-ración chip, the add flow

**Goal:** the ingredient rows and the add-ingredient affordance match the canvas
on both layouts.

**Web** (`RecetaEditorWebV2`): a grid "table" inside a surface card — columns
`Ingrediente | Cantidad | Tipo | ✕` (the canvas's leading drag column is
stripped, see Out of scope), a sunken uppercase header row, and per row: the
ingredient name (+ brand line where the ingredient has one), the quantity with
its unit derived from `ingredient.unit_type` (`'unit'` → "ud", else "g") — the
derivation the current editor already does — the **type chip**, and a remove
button.

**The type chip is the load-bearing bit.** `recipe_ingredients.per_serving`
already exists and the current editor already toggles it. The canvas renders it
as `por ración` (accent) vs `en total` (plain) on web, and the short `ración` /
`total` on mobile. Semantics, from the canvas's own note: a `per_serving`
ingredient is counted **per serving cooked** (multiplied by servings), the rest
are divided across the servings. **Do not re-derive this — `computeRecipeMacros`
in the frozen `macros.ts` is the authority; make the UI say what the code already
does.** If you find the chip's copy contradicts the maths, report it rather than
"fixing" either side.

**The add-ingredient footer.** Web: the inline search row at the bottom of the
table card (reuse `IngredientAutocomplete`'s logic — do not write a second
autocomplete). Mobile: the canvas replaces it with a full-width button that opens
a **bottom sheet** (`RecetaAddIngredienteMobile`): search field, live-filtered
results, the selected result expanding inline with a quantity stepper and a live
"+283 kcal" readout, and an "add to recipe" CTA. Build that sheet with
`ResponsiveDialog` (the shared kit's vaul/Radix wrapper) — not a hand-rolled one.
Strip the sheet's barcode button (wave 6).

The canvas's "¿No encuentras lo que buscas? → Crear un alimento nuevo" footer:
wire it only if a create-ingredient route already exists; otherwise strip it and
say so.

**Row delete** follows the canvas's inline convention: the row is replaced in
place by a confirm strip with **Cancelar on the outside**.

**Tier-2:** adding an ingredient through the flow puts a row in the table and
moves the live macros; toggling the type chip flips `per_serving` in what gets
saved; removing a row removes it.

## Task 3 — Close PR-A's two gaps

1. **"Duplicar" is unreachable for pooled recipes.** PR-A gated the edit action on
   ownership (recipes are a shared pool — R-01 — and `save_recipe` 400s on a
   recipe you did not create). The editor's "Duplicar" button was the only way to
   copy someone else's recipe into your own library, and it hung off that now-
   hidden path. **Add a "Duplicar" action to the read view** so the capability
   survives — it should land the user in the editor on a new, owned copy, exactly
   as the editor's button does today (read how `RecetaEditorPage` implements
   duplication and reuse it). Product-owner decision, taken 2026-07-12.
2. **A non-owner deep link to `/recipes/:id/edit`** still renders the editor and
   400s on save with a raw DB message. Nothing in the UI links there any more.
   Redirect to the read view when the user is not the recipe's creator
   (`canEditRecipe` in `src/features/recipes/ownership.ts` is the single source of
   truth — reuse it). Do not break the duplicate path from item 1.

**Tier-2:** a non-owner hitting `/recipes/:id/edit` lands on the read view; the
read view offers Duplicar on a recipe the user does not own; duplicating produces
an owned copy.
