## Global Constraints

Binding on every task. A violation is a failed review.

1. **Metric-only** (kg/cm/g). Prep time is integer **minutes**.
2. **DB is canonical; RLS is the sole security boundary.** Any >1-table atomic
   mutation is an RPC, `SECURITY INVOKER` + pinned `search_path`.
   `SECURITY DEFINER` is forbidden.
3. **Every new user-facing string in ES *and* EN** (`src/i18n/es/*.json` +
   `src/i18n/en/*.json`). No hardcoded copy in components.
4. **Do not touch `src/features/recipes/macros.ts`** — imported by ~30 files
   across diario/planning/templates/progreso. Frozen public API.
5. **Do not slim `listRecipes`' select.** `RecipeListItem.perServing` and
   `meal_types` are read by `AddRecipeDrawer` (wave 3) and `AddToDaySheet`
   (wave 2) off the already-fetched list. Removing either silently breaks them.
6. **Do not rename the `['recipes', …]` react-query keys** — invalidated
   cross-feature by `useSaveRecipe` / `useHideRecipe`.
7. **Reuse the shared kit before building anything new**: `PageShell`,
   `PaginationBar` + `usePagination` (shared with Exercises/Ingredients — do not
   fork), `ResponsiveDialog`, `AddToDaySheet`, and the shadcn primitives in
   `src/components/ui/`. Build UI with shadcn components whenever possible.
8. **`PageShell` mounts the mobile header AND `PageHeaderV2` simultaneously**
   (CSS hides one). In jsdom the title renders twice → page tests must use
   `getAllBy*`. This is by design, not a bug.
9. **Mobile artboard = base layout; web artboard = the `md:` and up layout.**
   Tailwind v4, mobile-first.
10. `pnpm lint`, `pnpm build`, `pnpm test` must all pass before a task is done.
11. **No AI/Claude attribution anywhere** — commits, comments, docs. Plain
    conventional commits.

## Task 1 — Prep time: schema, RPC, data layer

**Goal:** `recipes.prep_time_minutes` exists end to end, readable by the app.

**Migration** (`supabase/migrations/<ts>_r33_recipe_prep_time.sql`):

```sql
alter table public.recipes
  add column prep_time_minutes integer
    check (prep_time_minutes is null or prep_time_minutes > 0);
```

Nullable on purpose (nothing truthful to backfill; "no time recorded" is a
permanent legitimate state).

Then **drop and recreate `save_recipe`** with a new trailing param
`p_prep_time_minutes integer default null`. Adding a defaulted trailing param
without dropping would leave the old 7-arg body live and make PostgREST
ambiguous — the same reasoning as U-2's `p_meal_types`
(`supabase/migrations/20260526120000_u2_recipe_meal_types.sql`, which is the
template to copy: same `SECURITY INVOKER`, `set search_path to ''`,
fully-qualified tables, creator-ref insert on create, replace-children on
update). Drop the current overload explicitly:
`drop function if exists public.save_recipe(uuid, text, numeric, text, text, jsonb, text[]);`

**The param is written unconditionally on both insert and update** — passing
`null` clears the field, which is correct (user empties the input = "no time").

**Data layer:**
- Regenerate `src/types/database.ts` for the new column (do NOT hand-edit).
- `src/features/recipes/api.ts`: `fetchRecipe` already does `select('*')` →
  the column arrives free; add `prep_time_minutes` to the `saveRecipe` payload
  type and pass `p_prep_time_minutes` in the RPC call (always send it, even
  when null). Surface it on `RecipeListItem` too — the list's select is
  explicit, so add the column to it (constraint 5: add, never remove).
- `src/features/recipes/schema.ts`: extend the zod schema — optional, positive
  integer minutes, empty input → `null`. Unit/number conversion happens at the
  form boundary only (invariant 6).

**Tier-3 (pgTAP, `supabase/tests/`):** the check constraint rejects `0` and a
negative and accepts a positive value and `null`; `save_recipe` round-trips prep
time on create and on update, and can clear it back to `null`; the recreated RPC
still rejects an update to a recipe the caller does not own, and still replaces
children.

**Tier-1:** the schema's prep-time parsing/validation (empty → null, `"35"` →
35, `"0"` and negatives rejected, non-integer rejected).

**Out of scope:** any editor UI for the field (that is PR-B). This task makes
the field exist and be readable; the read view (Task 4) displays it.

## Task 2 — Shared recipe media placeholder

**Goal:** one component that fills every recipe "photo" slot in the app.

`recipes.photo_url` is dead (no bucket, no upload, the RPC never writes it) and
photo upload is out of scope for R-33. The canvas has no real photos either:
every recipe image is a **diagonal-stripe fill** whose hue varies per recipe.

Build `RecipeMediaPlaceholder` (in `src/features/recipes/components/`) —
the stripe fill with the **Recetas/utensils icon centred on it**, so it reads as
a deliberate placeholder, not a broken image. Props at minimum: the recipe id
(drives the hue) and a size/variant for the three call sites it will serve
(list card media band, mobile row thumbnail, detail hero).

- **Hue is derived deterministically from the recipe id** — same recipe, same
  colour, forever. Pure function, exported and unit-tested (Tier-1: same id →
  same hue across calls; different ids spread across the range; stable for a
  known id). Keep the hue range in the canvas's band (roughly 15–135) so the
  colours stay in the app's palette.
- Canvas source for the exact fill (port faithfully, standard Tailwind
  utilities + arbitrary values — the canvas is inline-style React, there is no
  Tailwind in it):
  `background: oklch(0.88 0.08 <hue>)` +
  `backgroundImage: repeating-linear-gradient(135deg, oklch(0.88 0.08 <hue>) 0 14px, oklch(0.84 0.09 <hue>) 14px 28px)`
  (mobile thumbnail uses a tighter 12px/24px stripe).
  See `recetas-web.jsx` (`RecipeCard`), `recetas-mobile.jsx`,
  `receta-editor-web.jsx` (`RecetaVistaWebV2` hero).
- Dark theme must not break — verify the fill and the icon stay legible.

**Out of scope:** anything to do with uploading or storing a real photo.

## Task 3 — Recetas list, redesigned

**Goal:** `/recipes` matches the canvas, mobile and web.

Current page: `src/pages/RecetasPage.tsx` (394 lines — the grid card, the list
row and `FilterChip` are all inline JSX; extract what the design needs).
Canvas: `RecetasWebV2` in `recetas-web.jsx` (web) and `RecetasMobile` in
`recetas-mobile.jsx` (mobile). Read both.

**Web (md+):** filter-chip row inside a surface card (Todas / Favoritas / the 5
meal types / the existing U-3 goal chips) with the sort label on the right;
responsive card grid (4 columns at the 1920 artboard); the existing
`PaginationBar` at the bottom.

**Mobile (base):** horizontal row cards — thumbnail left, name, kcal/ración,
macro row, and a `+ añadir al diario` CTA that **opens the existing wave-2
`AddToDaySheet`** (`src/features/diario/components/AddToDaySheet.tsx`) — do not
build a second sheet. Wrapping filter chips above the list.

**The "cutout" card style is not a notch.** The canvas's `CutoutCorner` SVG is
dead code. The real effect (defined only in `Nutrición Web.html`, not in
`tokens.css`) is: layered shadow that lifts 2px on hover, media zoom to 1.06,
and the "Leer más →" arrow gap widening 4px→7px — all `group-hover` utilities,
easing `cubic-bezier(0.23,1,0.32,1)`. Port it as a **shared** card style: the
Ingredientes editor (wave 6) reuses it.

Card anatomy, macro colours (use the shared macro-dot convention, **not** the
web artboard's tinted letters — the canvas screenshot note says dots win),
the tag pill and the favourite pin: follow the artboards.

**Favourites stay** (localStorage, `src/features/recipes/favorites.ts`). They
already work; removing them is a regression. The read view (Task 4) also needs
to toggle a favourite → **extract the localStorage read/write/toggle currently
inlined in `RecetasPage.tsx` into a shared hook** both pages use. Keep the
existing storage key and the existing pure helpers + their tests.

**Empty state:** the canvas has none — build one from its vocabulary (icon tile
in a sunken rounded square, 13px semibold muted title, dim hint, max-width ~260)
for both "no recipes yet" and "no results for this filter".

**Grid/list view toggle:** the canvas designed the grid only. Drop the toggle
(and its localStorage key) rather than ship an undesigned list view.

**Tier-2:** the page renders cards for the fetched recipes, the filter chips
narrow them, the empty state appears when nothing matches. (Note constraint 8 —
`getAllBy*`. Note the `component test supabase env` trap: mock the data hook,
do not let the component import a live supabase client in CI.)

## Task 4 — Route split + the read view

**Goal:** `/recipes/:id` becomes a read view; the editor moves to
`/recipes/:id/edit`.

**Routing** (`src/app/router.tsx`): `/recipes/:id` → new read page;
`/recipes/:id/edit` → the existing `RecetaEditorPage` (untouched by this task —
PR-B redesigns it); `/recipes/new` unchanged. Update `src/app/router.test.tsx`.

Retarget every link that currently opens the editor from a *reading* intent:
the list card (Task 3 already points at the read view), and the planner's
`RecipePeek` "ver receta completa" (`src/features/planning/components/
RecipePeek.tsx`, wave 3). Editing intents (the pencil action) go to `/edit`.
`RecetaEditorPage` currently navigates to `/recipes` after save — it should land
on the read view of the recipe it just saved (both on create and on update).

**The read page** — canvas: `RecetaVistaWebV2` (`receta-editor-web.jsx`) for
web, `RecetaVerMobile` (`recetas-mobile-detail.jsx`) for mobile. Sections:

- **Hero:** media placeholder (Task 2) + name + meal-type chip.
- **Meta strip:** raciones · **tiempo** · kcal/ración · nº ingredientes.
  **Omit the tiempo stat entirely when `prep_time_minutes` is null** — never
  render `0`, `—`, or a guess.
- **Macros card:** totals vs per-serving, **per-serving is the highlighted
  column**, plus the distribution bar. The bar's segments are **kcal share**
  (P×4, C×4, G×9 over total kcal), not gram share — a flex bar, `overflow:
  hidden`, rounded, no gaps. Pastel triad from the V2 artboard.
- **Ingredients card:** one row per ingredient, the `por ración` chip only where
  `per_serving` is true, quantity right-aligned with the unit derived from
  `ingredient.unit_type` (`'unit'` → "ud", else "g") — the same derivation the
  current editor does.
- **Preparación card:** the recipe's single `instructions` text rendered as
  **one numbered step ("1")** using the canvas's step-row anatomy (numbered
  circle + text), preserving the text's own line breaks. Structured multi-step
  recipes are R-36 — do not split the text into fake steps, and do not render
  the card at all when `instructions` is empty.
- **Actions:** favourite (shared hook from Task 3), "añadir al día" (opens the
  existing `AddToDaySheet`), and "editar" → `/recipes/:id/edit`.

Data comes from the existing `useRecipe(id)` — no new query, no new key.
Handle loading (skeleton) and not-found.

**Tier-2:** the read view renders name/macros/ingredients; the tiempo stat is
absent when null and present when set; `instructions` renders as step 1 and the
card is absent when the recipe has none; the edit action routes to `/edit`.
