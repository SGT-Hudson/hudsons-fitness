# R-33 tone core — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development. Steps use `- [ ]` checkboxes.

**Spec:** `docs/superpowers/specs/2026-07-09-r33-tone-core.md`. Read it — it holds every threshold, the golden vectors, and the three owner decisions.

**Goal:** Port the canvas semantic tone core to `src/core/nutritionTone.ts`, retire `src/lib/macroStatus.ts`, and rewire the four rendering consumers. Screen anatomy does not change; only which colour each bar/number takes.

**Tech stack:** React 18 + TS, Vite, Tailwind v4, Vitest + RTL (jsdom). Pure-logic convention: `src/core/X.ts` + colocated `src/core/X.test.ts`.

## Global Constraints

- No AI/Claude attribution anywhere — plain conventional commits, no `Co-Authored-By`, no "Generated with…" footer, no AI-process phrasing in code comments.
- Hard invariant 5: BMR, target weight and **the fat floor** are derived at render, never stored.
- No schema/RLS/RPC changes; no `.select()` string changes.
- No hardcoded palette classes or hex/oklch colour literals in components. Gates that must stay clean: `git grep -nE '#[0-9a-fA-F]{3,8}\b' -- 'src/**/*.tsx'` and `git grep -nE 'oklch\(' -- 'src/**/*.tsx'`.
- All user-facing strings in ES and EN. This plan introduces **no new i18n keys**.
- **`MacroBar`'s geometry must not change.** Its test pins 90.9 % / 9.0 % / 67.69 % — those numbers stay.
- Every task ends green: `pnpm lint` + the task's tests. Tasks 6 and 7 also run `pnpm build && pnpm test`.
- Metric-only (kg/g).

## Decisions locked by this plan (recorded in Task 7)

- Canvas tone names are kept verbatim (`good | onTarget | slightOver | low | over`) so the spec's worked examples transcribe 1:1. `over` means "outside range on the bad side", not "above target".
- `neutral` is added for a missing/non-positive target, which the canvas never models.
- `getExcessTone` takes only `status` — the canvas's `metric`/`phase` params are inert and are not ported.
- Fat's `pct > 0.10 → slightOver` has **no phase gate** (canvas code beats canvas prose, per parent spec §1).
- `FAT_FLOOR_G_PER_KG = 0.6`, applied to bodyweight.
- `ProteinBasis` is not a tone concept; it moves to `src/lib/macros.ts`.

### Task 1: `src/core/nutritionTone.ts` + golden-vector suite

**Files:** Create `src/core/nutritionTone.ts`, `src/core/nutritionTone.test.ts`.

**Interfaces (contracts — later tasks depend on these exactly):**

```ts
export type Tone = 'good' | 'onTarget' | 'slightOver' | 'low' | 'over' | 'neutral';
export type Excess = 'neutral' | 'warn' | 'bad';
export type PhaseType = 'cut' | 'maintenance' | 'bulk';
export type Metric = 'kcal' | 'protein' | 'carbs' | 'fat' | 'fiber';

export interface ToneStatus {
  tone: Tone;
  excess: Excess;
  remaining: number;
  overG: number;
  minFloorG?: number;
}

export const FAT_FLOOR_G_PER_KG = 0.6;
export function essentialFatFloorG(weightKg: number): number;
export function getKcalStatus(consumed: number, target: number, phase: PhaseType): Tone;
export function getMacroStatus(metric: Exclude<Metric, 'kcal'>, consumed: number, target: number, phase: PhaseType, fatFloorG?: number): Tone;
export function getExcessTone(status: Tone): Excess;
export function classify(metric: Metric, consumed: number, target: number | undefined, phase: PhaseType | undefined, opts?: { fatFloorG?: number }): ToneStatus;
```

- [ ] **Step 1: Write the failing golden-vector test**

Transcribe spec §5 verbatim into `it.each` tables — one describe per metric, plus a `MiniWeek` integration case. Then add the boundary tests the spec enumerates (each threshold at exactly its edge; `target <= 0`; `target` undefined; `consumed === 0`; `essentialFatFloorG(0)`, `(NaN)`, `(-5)`).

Run: `pnpm vitest run src/core/nutritionTone.test.ts` → FAIL (module absent).

- [ ] **Step 2: Implement**

Port the four functions from `planificador-tone.jsx` exactly as quoted in spec §2.2. `classify` is the app-facing wrapper: it guards a missing/non-positive target (→ `neutral`/`neutral`, `remaining = 0`, `overG = 0`) *before* any division, dispatches to `getKcalStatus`/`getMacroStatus`, derives `excess` via `getExcessTone`, and sets `minFloorG` only for `metric === 'fat'` when a floor was supplied.

`phase` undefined in `classify` → default `'cut'` (matches the retired module's behaviour; note it in a comment).

`essentialFatFloorG(weightKg)` = `round(FAT_FLOOR_G_PER_KG * weightKg)`, `0` when the input is not a finite positive number.

**Files:** Modify `docs/decisions.md`. Check whether `docs/conventions.md` documents the macro-tone rules; if it does, add the `> ⚠ Changing — see R-33` marker only if one is not already there.

`docs/decisions.md` uses `## D-Fxx — Title` headings with `**Ruling:** / **Why:** / **Status:**` bodies. Match that. D-F16 is currently the last ID — verify before numbering.

- [ ] **Step 1: D-F17** — the canvas tone core replaces `macroStatus.ts`. Ruling: canvas thresholds and tone vocabulary win; `budget` (blue) is dropped so under-target in a cut simply reads green; protein under target now warns (amber at −3 %, red at −10 %); carbs in bulk read green rather than grey; maintenance overshoot is amber, not red. Why: the parent spec's source-authority order puts the canvas above the app's improvised bands, and the app is pre-production so no migration is owed. Also note the two ports-with-judgement: `getExcessTone`'s inert `metric`/`phase` params are dropped, and fat's +10 % rule is left ungated by phase because the canvas code, not its prose, is authoritative.
- [ ] **Step 2: D-F18** — the fat essential floor is `FAT_FLOOR_G_PER_KG = 0.6` applied to bodyweight, derived at render, never stored. Why: the canvas leaves the provenance undefined (always injected, always the literal 48 in fixtures); the shipped app derived it from target kcal, which makes a physiological floor move when you eat less. All three definitions coincide near 48 g at 80 kg / 2180 kcal; they diverge exactly where the energy-based one is wrong.
- [ ] **Step 3: Amend D-F15** to *resolved*. Its follow-up was "reconcile the invented dark `--tone-*`/`--excess-*` values once the tone core lands upstream in the canvas". There is nothing upstream: the canvas has no such tokens — `TONE`/`EXCESS` are hardcoded OKLCH literals in `planificador-tone.jsx`, light-only. We own these slots; the light values already match the canvas literals exactly. Add the resolution to its Status line rather than rewriting the entry.
